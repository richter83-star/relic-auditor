# Upgrading to Relic Auditor 1.0.1

v1.0.1 is a reconciliation release candidate. The upgrade path must preserve user configuration and must not mix files from the disconnected old v1.0.0 repository history with the validated v0.12 lineage.

## Windows installed builds

The v1.0.1 installer is designed as an in-place per-user replacement. The Windows RC lifecycle verifies that a reinstall/upgrade:

- preserves Relic user configuration under the per-user configuration area;
- removes obsolete managed GUI and CLI runtime files;
- keeps the selected CLI PATH entry correct;
- reports the new `relic 1.0.1` version;
- leaves user configuration in place when later uninstalled; and
- removes the installer-owned CLI PATH entry on uninstall.

The current RC is unsigned. Automatic updater installation therefore remains intentionally blocked. Until trusted Authenticode signing and the stable manifest are provisioned, use only explicitly verified manual RC artifacts.

## Source installs

From an exact v1.0.1 source checkout:

```bash
python -m pip install -e ".[all]"
relic --version
```

Expected version output:

```text
relic 1.0.1
```

Do not copy Python package directories from an old disconnected v1.0.0 checkout over a v0.12 or v1.0.1 installation. Install from one coherent source tree.

## CLI compatibility

Existing v0.12 CLI commands remain routed through the preserved v0.12 command implementation. v1.0.1 adds:

```bash
relic resurrect /path/to/estate --output /path/to/resurrection-report
```

`audit --resurrection` is not part of the current RC interface. Scripts should use the standalone command.

## Reports and managed workspaces

Historical reports remain data; do not treat an old report as evidence that the current target is unchanged. Build Pack approval and export rules continue to require current hashes / rescan state where the contract demands it.

Assisted Build sessions remain separate managed workspaces. Upgrading Relic does not grant new capabilities to an existing session and does not authorize writes to the scanned source target.

## Repository maintainers

The unified v1.0.1 branch descends from the validated v0.12 line. The old `main` / v1.0.0 history has no common ancestor with that line.

Do not solve this by a casual `git merge --allow-unrelated-histories` and accept whichever files win conflicts. The final default-branch strategy requires an explicit, reviewed decision after exact-head RC validation.

Before a public release:

1. verify the exact intended release commit;
2. require green source and Windows lifecycle checks for that exact commit;
3. verify the frozen source hash and installer manifest from the workflow artifact;
4. decide and execute the default-branch reconciliation under explicit authorization;
5. apply branch protection / required checks;
6. provision signing/stable-update trust as required; and
7. only then create the release tag / GitHub Release or publish installer artifacts under explicit authorization.
